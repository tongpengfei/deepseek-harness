# Agent Note: 场景应用共用一个客户端 Slot

Status: implemented

[English](2026-09-20-scenario-apps-client-slot.md) | 中文

## 问题

面向具体场景的界面需要在 Web 客户端中有一个易发现的入口。若每个界面各占一个侧栏条目，导航会随已安装场景不断增长；若建立独立组件注册表，又会重复客户端 Slot 系统已有的生命周期、排序、遮蔽和错误隔离行为。

## 决策

默认 Web 组合包含一个 Apps 外壳，其中只有一个侧栏入口和一个 root 作用域主面板。该面板声明 root 作用域的 `apps.item` 列表 Slot。浏览器插件通过一个 Slot 条目贡献应用，并提供稳定 id、跟随语言变化的标题、顺序、摘要视图和页面视图。Apps 外壳持有目录选中态与导航；贡献插件持有场景状态，并调用现有服务、Remote、Session 或嵌套 Slot 实现行为。

应用是可信的浏览器插件代码。其 bundle 的安装、启用、停用和移除仍由插件管理器负责，Slot 条目跟随贡献插件的 effect 生命周期。空目录是有效状态。此决策不增加面向模型的输入，也不增加新的 Host 执行路径。

## 考虑过的替代方案

| 替代方案 | 未采用原因 |
|---|---|
| 每个应用各自注册侧栏和主面板 | 导航本身会变成目录，场景发现入口分散，并重复通用页面行为。 |
| 建立第二套应用组件注册表 | 这会形成平行扩展机制，并重新实现 Slot 的生命周期与隔离。 |
| 通过 `cordis-client-runner` 运行生成包 | 该运行时是瞬时的纯 JavaScript 开发表面，不能提供此处需要的类型化、可恢复插件包。 |
| 在首版加入 tclaw iframe 或静态页面桥 | 资源、信任、权限、持久化以及浏览器到 Host 的消息传递需要独立的兼容性与安全决策。 |

## 结果

场景提供方打包普通 DSH 客户端插件并注册一个 `apps.item` 条目。目录始终只占一个导航目的地，卸载或 HMR 无需 Apps 外壳专门清理即可移除应用。需要持久状态或智能体执行的提供方组合现有 DSH 能力，而不会获得 Apps 专用执行 API。原样运行已有 tclaw 包仍属于后续工作。

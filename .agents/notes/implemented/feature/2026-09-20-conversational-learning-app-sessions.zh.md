# Agent Note: 对话式学习应用使用专用 Session

Status: implemented

[English](2026-09-20-conversational-learning-app-sessions.md) | 中文

## 问题

学习应用需要持续的教学对话，而不是一组静态题目。复用主对话会把课程 prompt 与用户原本在 DSH 中执行的任务混在一起；把消息保存在应用状态中则会失去 Session 的持久性、流式响应、取消能力和正常历史访问。不同编程语言课程还需要共享同一种交互模型，同时不能假装已经执行了学习者的代码。

## 决策

C 语言学习应用使用随附的 `learning` Agent preset 创建并持有一个专用 DSH Session。该 preset 包含完整的新手导师 persona，不注入工作区运行时上下文，也不暴露工具。浏览器 store 保存 Session id、课程选择和由学习者手动确认的完成状态；Session 日志持有学习者消息、导师回复和面向模型的课程指令。重置应用会释放引用并删除浏览器中的关联，但不会删除 Session。

应用会在 Session 启动和学习者切换课程时发送一条已记录的控制消息。每节课只提供一个新知识点、一个重点语法形式、一个最小示例和一道延后给出的练习。控制消息把教学分成讲解、澄清、练习、点评和可选扩展阶段：导师先只讲当前知识点并确认学习者是否准备好，得到确认后给一道练习，首次讲解不引入后续课程。它也禁止声称已编译或执行代码。学习者时间线只投影真正来自用户的消息、助手最终文本和助手实时文本；带标记的控制消息及插件注入的 user-role 上下文不会进入界面。普通回答、问题、快捷操作和粘贴的代码都使用同一个 Session prompt 操作。

课程定义包含语言元数据和课程依据，对话、Session 所有权、进度和渲染流程则保持与语言无关。因此 Python 或 Go 应用可以提供不同的课程数据，而不需要创建另一套对话子系统。

本决策组合现有的 [Apps Slot](../architecture/2026-09-20-scenario-apps-client-slot.zh.md) 和[客户端 Session 引用](../architecture/2026-09-15-client-session-references.zh.md)机制，不增加 Apps 专用 Host API，也不增加本地编译器能力。

## 考虑过的替代方案

**复用主对话 Session。** 课程控制消息和学习历史会成为无关任务的一部分，而且关闭应用时无法说明哪个视图持有 Session 引用。

**在浏览器状态中保存独立聊天记录。** 这会重复实现 Session 持久化和流式语义，无法进入正常 Session 历史，并且需要另一套恢复和取消实现。

**使用默认编码 preset 并隐藏其注入消息。** UI 过滤之后，模型仍会收到工作区指令、skill 目录和工具 schema。这些输入浪费上下文，可能与导师角色冲突，还会授予学习应用不使用的能力。

**每课创建一个 Session。** 课程边界会丢失导师对学习者问题的了解，也会让一门短课表现为多个互不相关的任务。

**保留静态选择题检查。** 固定题目无法调整讲解、分析粘贴的代码或引导学习者澄清误解，因此不能提供所需的对话式学习体验。

**在本地编译或执行学习者代码。** 执行需要单独的沙箱、工具和信任决策。导师只分析文本，并明确说明它没有运行程序。

## 结果

学习对话可以跨应用重新挂载保留，并继续通过正常 Session 系统访问。应用可以停止正在生成的回复、重新连接已持有的 Session，并渲染持久或流式 Markdown，而不需要另一个消息 store。学习者在整个课程中保留一个对话上下文，课程完成状态则由学习者明确确认，不根据模型判断推断。专用 preset 会让编码 Agent 指令和能力远离导师请求，并使“不执行代码”成为结构约束，而不只是一句 prompt。

开始第一课需要配置模型 provider，每轮教学也会产生一次正常模型请求。即使对话是持久的，不同浏览器配置中的本地课程进度仍可能不一致。由于没有编译器验证导师的答案，导师对代码的分析可能出错。
